## B1【中·确证前视】⚠️ cos IC 权重窗剔尾长度写死为 1，开盘 h 步口径需剔 h+1

**位置**：`live_v51.py:91`、`eval_open_horizons.py:79`、`scripts/实验/自适应窗实验.py:66`、`自适应窗实验2.py:78`。
对照 `final_signal.py:96` 的同一行是**正确的**（走 close 口径的 `次日收益`，h=1，剔 1 行恰好）。

```python
r次 = 面板["open"]["zz1000"].pct_change(h, fill_method=None).shift(-(h + 1))
#  r次[t] = open[t+1+h]/open[t+1] − 1        ← 用到 t+1+h 日的开盘价
c = _cos(p表[f].loc[起:cutoff].iloc[:-1], r次.loc[起:cutoff].iloc[:-1])   # 只丢 1 行
```

权重在本季首日开盘生效，决策时点只知道 ≤ cutoff 的价格，末 h+1 行全部不可得。

**幅度——两个独立测量，要一起看**
- 逐库单独回测 Δ年化：h1 0.0pp / h2 0.1 / h3 0.3 / h4 0.5 / h5 0.4 / h6 1.9 / h7 0.6
- 六库合奏（h1+h5 各占 1/3）：年化 30.1%→30.1%、夏普 1.45→1.44、回撤 −20.6%→−20.9%

两者不矛盾：合奏只含泄漏最小的两个 h。**结论：这是真前视，但对已发布数字实质无影响（<0.1pp）。**
按修正幅度重排七个 h：27.0 / 30.4 / 29.1 / 24.5 / **36.6** / 22.8 / 19.9 —— **h5 仍居首，选型不变。**

**修复**：不要用写死的位置切片，让剔尾长度跟着 h 走：

```python
末 = 日历[日历.searchsorted(cutoff) - (h + 1)]      # 决策时点可得的最后一条 Y
c = _cos(p表[f].loc[起:末], r次.loc[起:末])
```

h=1 时退化为现状。把「**剔尾条数 = h+1**」写进预注册口径表，避免下次再按 close 口径复制。

## B2【中】⚠️ cos IC 无最小样本量门槛

**位置**：`live_v51.py:46-49,91` / `eval_open_horizons.py:38-41,79` / `final_signal.py:70-73,96`
——`_cos`/`cos_ic` 内 `dropna()` 之后没有任何 `len` 检查。

因子信号可能因 `div` 分母近零、rolling 窗未满等原因在 trailing 12 月里只剩个位数有效观测。
cos IC 是比值，样本少时数值照样落在 (0,1]，于是「几乎无有效信号」的因子凭少数巧合样本
拿到全库最大权重（实测最大 8.97%），再把这份权重变成对组合信号的稀释。

**方向是低估**——加上门槛后成绩变好。

**修复**：`_cos`/`cos_ic` 返回配对样本数，权重环节 `if n < 门槛: continue`，
建议门槛 **120 对（≈半年）**，并入预注册阈值清单。另对 `p表` 窗口 NaN 率设上限（非 NaN <0.5 不给权重）。

## E2 ✅ 权重被 `ts_std` 族垄断；挖矿的真实贡献在夏普不在年化

**末季生产权重中含 `ts_std` 的份额**（我复算，与审计员逐项吻合）：

| 库 | h1 | h1_s42 | h1_s137 | h5 | h5_s42 | h5_s137 | **六库并池** |
|---|---|---|---|---|---|---|---|
| ts_std 占比 | 88.7% | 86.7% | 74.3% | 69.9% | 43.7% | 43.1% | **67.7%** |

计入 `ts_zscore`/`ts_vr5`/`disp` 等的整个波动族 = **81.5%**。

**直接对照实验**（我复算，同一 open→open 结算、同一双 rank40 + tanh(Φ⁻¹) 映射）：

| 策略 | 年化 | 夏普 | 回撤 | 卡玛 |
|---|---|---|---|---|
| **六库合奏 p6（无状态层）** | **29.5%** | **1.45** | −20.0% | **1.48** |
| 手搓一行 `ts_std(returns,20)` | 28.4% | 1.28 | −21.4% | 1.32 |
| 手搓一行 `ts_std(returns,10)` | 26.1% | 1.27 | −18.7% | 1.39 |
| 手搓一行 `ts_std(returns,5)` | 19.2% | 0.96 | −19.4% | 0.99 |

**回归（六库日收益 ~ 手搓因子日收益）**

| 基准 | beta | corr | R² | alpha 年化 | t |
|---|---|---|---|---|---|
| std5 | 0.79 | 0.785 | 0.62 | **12.4%** | **3.40** |
| std10 | 0.76 | 0.775 | 0.60 | 8.5% | 2.29 |
| std20 | 0.70 | 0.775 | 0.60 | 8.5% | 2.29 |

**怎么读这组数**：
- 挖矿**不是白做**——alpha 在 t=2.3~3.4 显著，夏普 1.28→**1.45**、卡玛 1.32→**1.48**；
- 但**原始年化只高 1.1pp**（29.5 vs 28.4），R²=0.60 意味着六库日收益 60% 的方差由一行手搓因子解释；
- 「1200 因子 / 六库」的实质是**一个短窗已实现波动方向 + 8~12pp/年的 beta 调整增量**，
  六库**共享同一个失效模式**（波动率结构变化）。

**该改的是叙述**：容量、失效场景、风险描述要按「波动溢价单一方向 + 增量 alpha」重写，
不能继续按「1200 个独立因子的集成」讲。

**可选修复**（属新增门槛，须重新预注册后整体重挖再对比）：HOF 筛选或入库阶段加算子族配额
（如含 `ts_std` 的因子累计权重上限 40%），或让候选先对 `ts_std(returns,{3,5,10,20})` 回归、用残差 IC 过入库线。

## 背景

档案 `02_截面叶子/README.md:74` 白纸黑字「**主门槛未过**：28.9/1.42 vs 30.8/1.46」，

## 实验一：合奏层跨库去重（E1 的修复）

三条对照隔离「架构变化」与「去重本身」。去重的相关矩阵只用 `[cutoff−2年, cutoff]`，不含未来。

| 口径 | 年化 | 夏普 | 回撤 | 卡玛 | 2022+夏普 |
|---|---|---|---|---|---|
| A 六库各自双 rank 后取均值（现行生产） | 32.3% | 1.50 | −16.0% | 2.01 | 1.15 |
| B 并池不去重，单条 rank40 | 35.1% | 1.51 | −17.4% | 2.02 | 1.16 |
| C 并池 + 跨库去重（\|corr\|>0.95 连通聚类，团簇按 1 个位置计） | 35.5% | 1.53 | −17.4% | 2.04 | 1.16 |

**B→C 是纯去重效果：+0.4pp 年化 / +0.02 夏普 / 回撤不变。** 去重平均丢 16.4% 的池
（243→203，末季 501→419）。

**结论：E1 的结构性发现成立，但其 P&L 后果可忽略。** 跨库重复是真的，
可「修掉它」既不能救也不能定新四库的罪 —— 去重是这个决策的**无关变量**。

（A→B 的 +2.8pp 是架构变化，不是去重。但它同时把回撤从 −16.0 恶化到 −17.4，
且属于新的同样本择优，**不得据此改架构** —— 记为 v6 候选，需预注册 + 多种子验证。）

## 环境对齐（开跑前的坑，记下来免得下次再踩）

| 项 | 发现 | 处理 |
|---|---|---|
| Python | pod 默认 `python3` 是 **3.8**，而 `expr.py` 用 `str.removeprefix`（3.9+） | 显式用 `python3.11`（与本地 3.11.1 同版本） |
| pandas | pip 默认装成 **3.0.5**，本地是 **2.3.3** —— 跨大版本（copy-on-write、字符串 dtype 默认值都变了）挖出来的库拿回本地重放很可能对不上 | 全部钉死：`pandas==2.3.3 numpy==2.3.3 scipy==1.17.0 arch==8.0.0` |
| `arch` | pod 无此包 → `ArgarchRecorder.extend` 报 `ModuleNotFoundError`，整条挖矿链跑不起来 | 装 8.0.0（与本地一致） |

## ⚠️ 跨机不能逐位复现（新发现，非本次引入）

同一份代码、同一份数据、同一套依赖版本，在本地与 pod 上跑**同一个 smoke**（GA 40×5，至 2016-06-30）：

| | 名册行数 | md5 | 2016Q2 在役 |
|---|---|---|---|
| 本地（macOS / Accelerate） | 125 | `c5604b6f…` | 107 |
| pod（Linux / OpenBLAS） | 125 | `60c723af…` | 108 |

**逐项比对**：共同因子 **116/125（93%）**，各有 9 个独有；
**所有共同因子的 `sign` / `status` / `admit_q` / `yellow` 零差异，13 个元老也零差异**。

**排查**：`PYTHONHASHSEED` 不是原因（本地用 0 与 12345 跑出同一个 md5）；元老零差异说明不是 `arch`/GARCH。
剩下的解释是 **BLAS/LAPACK 实现差异**（Apple Accelerate vs OpenBLAS）在 `np.linalg.lstsq`
与 spearman 上的末位差，扰动了边缘处的 GA 适应度比较与闸门判定。

**结论：不阻塞重挖，但必须记录。**
- 7% 的名册分歧**小于**项目已记录的种子噪音带（±2~4pp/年），且所有留下来的因子治理字段完全一致；
- 本次验收判据是**结构性**的（类库入库 0→非0、复职 0→非0），数值噪音解释不了；
- 但要清醒：**「重挖能得到同一个库」在跨机意义上是假的**。这是既有性质（历史上所有库都是 pod 挖的），
  不是本次引入。真正的含义是——**库本身是产物，一旦定下就到哪都能确定性重放**
  （PIT 测试已证 `live_v51` 逐位复现 `v51_逐日.csv`），但「重跑挖矿」不是幂等操作。
- 另一层影响:新库(A批修复后)与旧库(修复前)分别挖在**不同的 pod** 上,
  两者之差里混着机器噪音。故不得用细微的成绩差来论证修复的好坏,只能用结构性判据。
